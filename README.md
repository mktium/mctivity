# mctivity v1.2.0

> Status: `v1.2.0` is a preview/source release for controlled lab evaluation and integration testing. It is not a certified safety system and must not be used as the sole protection layer for machinery.

`mctivity` is a dual-axis EtherCAT motion-control software stack including:

- motion daemon
- Web HMI
- modular assembly layer
- command-line control tool

This version establishes the first modular baseline of the project while keeping the existing axis-control workflow intact.

Core updates:

- modular assembly chain is available through `profile + module + feature registry`
- incremental displacement is available as an independent feature
- HMI mode entries now follow actual assembly state
- torque mode is registered in the same feature assembly path as the other axis modes
- FV3 dual-axis access is gated by the `full` profile capability set
- API commands are validated, field-ordered, and sanitized before being forwarded to `motiond`

## Platform

- Linux
- systemd
- Python 3
- IgH EtherCAT Master development/runtime environment
- tested with Python 3.12

## Safety

- The Web HMI now listens on `127.0.0.1` by default.
- Use `MCTIVITY_WEB_HOST=0.0.0.0` only in a controlled local network. Add LAN hostnames or IP addresses through `MCTIVITY_ALLOWED_HOSTS`, and set `MCTIVITY_API_TOKEN` for shared-network use.
- If `MCTIVITY_API_TOKEN` is set, `POST /api/command` and `GET/POST /api/ui_state` require authentication. The browser HMI can send it from the top-bar API Token field.
- `POST /api/command` and `/api/ui_state` require `Content-Type: application/json`; cross-origin browser POST requests are rejected.
- Motion-control software can move real hardware. Confirm E-stop, limit protection, and servo parameters before enabling motion.

## Deployment Notes

- systemd examples assume a dedicated `mctivity:mctivity` user and group
- UI state is intended to live in `/var/lib/mctivity/` under systemd
- see [Assembly Quickstart](docs/assembly-quickstart.md) for profile switching and verification

## Build and Start

Build motion daemon in an EtherCAT development environment:

```bash
cd mctivity_pdo_monitor
make
```

Start the HMI manually with the default local-only binding:

```bash
cd mctivity_hmi
python3 mctivity_hmi.py
```

Install to a systemd-based target:

```bash
sudo groupadd --system mctivity || true
sudo useradd --system --gid mctivity --home-dir /var/lib/mctivity --create-home mctivity || true
sudo mkdir -p /opt/mctivity
sudo cp -a . /opt/mctivity
sudo cp systemd/99-ethercat-mctivity.rules /etc/udev/rules.d/
sudo udevadm control --reload-rules
sudo udevadm trigger
sudo cp systemd/mctivity-motiond.service /etc/systemd/system/
sudo cp systemd/mctivity-hmi.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now mctivity-motiond.service
sudo systemctl enable --now mctivity-hmi.service
```

`motiond` expects compact JSON-line commands generated by `mctivity_hmi.py` or `mctivity_ctl.py`. It is not a general-purpose JSON parser. Public API requests should go through the HMI service so command validation, capability checks, payload sanitization, and numeric validation are applied first.

`mctivity_ctl.py` is a local low-level daemon client. It connects directly to `motiond` and bypasses HMI profile/capability gating.

`mctivity_motiond` in v1.2.0 is built for the current two-slave EtherCAT topology: MCTIVITY axis at slave position 0 and FV3 axis at slave position 1. `minimal` and `standard` profiles hide or reject FV3 at the HMI/API layer, but they do not change the EtherCAT topology expected by `motiond`.

Motion safety limits can be tightened or relaxed with environment variables:

- `MCTIVITY_MAX_JOG_VELOCITY_CPS`
- `MCTIVITY_MAX_CURVE_VELOCITY_CPS`
- `MCTIVITY_MAX_CURVE_ACCEL_COUNTS_S2`
- `MCTIVITY_MAX_SPEED_RPM`
- `MCTIVITY_MAX_ACCEL_RPM_S`
- `MCTIVITY_MAX_MOVE_MS`
- `MCTIVITY_MAX_GEAR_RATIO`
- `MCTIVITY_MAX_TORQUE_PERCENT`

Before publishing or packaging a release, run:

```bash
./scripts/mctivity-release-preflight.sh
```
